# Open-source reuse policy — owner approved 2026-11-27
Before implementing each substantial capability, inspect existing Pocket Genesis mechanics and search for suitable existing open-source implementations. Prefer reuse when it reduces work without compromising the fixed 100x60 world, deterministic ticks, observer-only interface, stable citizen identity, bounded memory, offline operation or portable persistence. Do not import a complete competing simulation engine merely because it has a desired feature. The core simulation remains authoritative; external rendering cannot drive ticks or mutate world state.

## Admission gate
1. Define the exact missing capability and data/state contract; identify reusable internal primitives.
2. Review upstream source, license, exact revision, dependencies, assets, build options, maintenance and known issues. Prefer MIT/BSD/Apache-2.0 with compatible terms. Public visibility alone is not permission. Escalate unclear licenses, copyleft obligations, incompatible dependencies or paid components before adoption.
3. Choose direct reuse, a small adapter, independently implemented algorithm informed by references, or no reuse. Record the reason, upstream URL, reviewed files, revision, license and any copied/modified portions. Keep required notices and third-party attribution; review assets separately. Do not label reference-only work as imported code.
4. Pin accepted dependency revisions and avoid automatic unreviewed updates. Keep device-specific adapters outside the portable core. No desktop runtime, network service, unnecessary allocations, dynamic per-animal object graph or unbounded thread pool on the Elecrow.
5. Require relevant host regression, deterministic replay/resource invariants, measured memory/tick cost, and actual target compile/physical evidence before claiming hardware compatibility. Floating-point terrain must be checked across supported targets; persist authoritative generated terrain and version generation rules if needed. No official-world reset or migration without the existing release gates.

## Livestock decision
Review of our core/wildlife.hpp and wildlife_movement.hpp shows existing species groups, bounded local migration, shared food/water grazing, resource-limited births, hunting and displacement accounting. Reuse those primitives; do not introduce a second animal simulation or individual genome system. A future domestication increment must transfer actual wild animals into bounded managed groups at appropriate completed enclosures, account for capture, survival, food, water, breeding and harvest, and mark developed land through real construction. No free livestock spawning, no unlimited breeding, no unexplained population correction. Upstream ecosystems above inform the design comparison, but their code has not been imported or source-level certified. Keep crop-loss verification first, then implement this shared mechanism in a disposable integration probe and verify performance.
